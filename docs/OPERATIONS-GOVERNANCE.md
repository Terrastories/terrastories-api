# Operations governance: secrets, privacy, retention, incident response

**Status:** operator documentation for issue #150, subordinate to `docs/SPEC-V2.md`. Every retention number below is quoted from the spec (mainly Sections 5-7, 10) — this document may not drift from those values. Secret values live only in environment variables or platform secret stores, never in files, the repository, logs, or reports.

## 1. Startup configuration gate (#150)

Production deployments must fail closed on insecure or default critical configuration. `src/config/v2-runtime.ts` implements one shared validator used by both V2 entrypoints:

- **Node** (`src/hono-server.ts`): runs at startup before any adapter or database is opened; a refusal exits the process non-zero.
- **Workers** (`src/worker.ts`): runs at first request per binding set; a refusal returns `503 {"error":"Service unavailable"}` with `Cache-Control: no-store` and logs one line naming the offending settings.

Mode selection: `NODE_ENV` (Node) and `ENVIRONMENT` (Workers binding) accept `development`, `test`, `production`, `field-kit`, `offline`; **unset means production**; unknown values are refused. `production`, `field-kit`, and `offline` enforce the production rules; only `development` and `test` relax them.

| Setting (Node / Workers)               | Refused when                                                                                                                                      |
| -------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| `NODE_ENV` / `ENVIRONMENT`             | value is not one of the five known modes (unset is allowed and means production)                                                                  |
| `HONO_PUBLIC_ORIGIN` / `PUBLIC_ORIGIN` | missing in a production-like mode; not an exact origin; not `http(s)`; a template placeholder; a loopback host; `http` where https is required    |
| `HONO_CORS_ORIGINS` / `CORS_ORIGINS`   | any entry is a wildcard (`*`), not an exact origin, a placeholder, or `http` where https is required (credentialed CORS needs an exact allowlist) |
| session cookie `Secure` flag           | disabled where https is required (development/test may disable it; the field-kit plain-HTTP opt-in may)                                           |
| `HONO_PORT` (Node only)                | not an integer in 1-65535                                                                                                                         |
| `DB` / `MEDIA` bindings (Workers only) | missing from the binding set                                                                                                                      |

Messages name the setting, never its value. Placeholder detection covers, case-insensitively: `change-me`/`change_me`/`changeme`, `replace-with`/`replace_with`/`replacewith`, `00000000-`, `placeholder`, hostnames starting `your-`/`replace`/`change-me`, the documentation hosts `example.org`/`.com`/`.net` and their subdomains, the reserved TLDs `.example`, `.invalid`, `.test`, `.localhost`, and (in production-like modes) loopback hosts. The committed `wrangler.jsonc` is a template whose `replace-with-*` names and `https://example.org` origin are exactly what the gate refuses in production.

**Plain-HTTP exception (SPEC-V2 §7).** Field kits serve HTTPS by default via a device-local CA. Plain HTTP on a trusted LAN is allowed only on Node `field-kit`/`offline` modes with the explicit opt-in `HONO_ALLOW_PLAIN_HTTP=true`; it is never available on Workers or in `production` mode, and while enabled the admin UI shows a persistent warning and the readiness report flags the build (SPEC-V2 §7). Non-Secure cookies follow the same boundary.

**Layering with the V1 gate.** On Node, `src/shared/config/schema.ts` still rejects missing, shipped-placeholder, or sub-32-character `JWT_SECRET`/`SESSION_SECRET` in production/field-kit modes when the shared database bootstrap loads configuration; the V2 gate fires first at startup. V2 itself has no configuration secret yet — sessions are 256-bit random tokens stored only as SHA-256 (SPEC-V2 §6.8) — so there is no length rule to enforce today; the first V2 config secret (the prelogin `serverSecret`, SPEC-V2 §7) must join this validator with a ≥32-character rule and this inventory.

**Tests:** `tests/config/v2-runtime.test.ts` (every rule, plus dev/test acceptance), `tests/hono/worker-config.test.ts` (workerd serve refusals and valid-production serving), `tests/config/v2-runtime-startup.test.ts` (Node process exits non-zero, before the database opens).

## 3. Rotation and revocation runbooks

Each runbook ends with a verification step. "Automated" cites the test that proves the property; where no automated test exists yet, the manual check is stated and the owning work is named.

**R1 — V2 sessions (revocation).** The account logs out, or calls revoke-all; a community admin revokes a member's device sessions by metadata; user/community authority changes delete sessions via database triggers (SPEC-V2 §6.8).
_Verify (automated):_ `tests/hono/foundation.test.ts` and `tests/hono/worker.test.ts` prove the presented cookie stops authenticating immediately after logout/revoke, that login rotation binds a fresh row while the old token fails, and that requests fail closed when authoritative session state is unreadable. _Operator spot check:_ replay the old cookie — expect `401`.

**R2 — `JWT_SECRET` / `SESSION_SECRET` (V1 runtime).** Generate a new value (`openssl rand -base64 48`), replace it in the deployment environment (never in a file or the repository), and restart the deployment. Compose files require both variables (`:?` guard).
_Verify (automated):_ the production config gate rejects placeholders and values shorter than 32 characters — `tests/config.test.ts` ("rejects shipped production placeholder", "must be at least 32 characters in production"). _After rotation:_ previously issued tokens and sessions stop validating — replay an old session cookie/authorization, expect `401`.

**R3 — PostgreSQL credential.** `ALTER ROLE terrastories WITH PASSWORD '<new>';` (from an admin session), update `DATABASE_URL` in the deployment environment, restart. V2 sessions are database-backed and survive the rotation.
_Verify:_ connect with the old URL — authentication must fail; with the new deployment up, `GET /ready` returns `{"status":"ready"}`.

**R4 — Field-kit local CA key.** Generate a replacement CA, reissue the certificate covering every configured host name and IP, re-enroll devices against the new CA fingerprint (shown in the admin UI and on the printed recovery sheet), then destroy the old key file. A leaked key requires exactly this: replace the CA and re-key all enrolled devices (SPEC-V2 §7).
_Verify:_ a device still pinned to the old fingerprint must fail TLS trust; the readiness report shows the new fingerprint and continues to flag the build if the plain-HTTP exception is enabled.

**R5 — Cloudflare API token.** Roll the token in the Cloudflare dashboard (keep it scoped), update the operator environment.
_Verify:_ `npx wrangler whoami` fails with the old token and succeeds with the new one (command outline in `docs/CLOUDFLARE-STAGING.md`).

**R6 — Recovery codes.** The account holder regenerates the set through the authenticated step-up action, which re-verifies the current password; regeneration marks every earlier code superseded (SPEC-V2 §6.8).
_Verify:_ an earlier code must fail redemption with the uniform non-enumerating login failure. An automated regeneration-supersession test lands with the authentication work (#137/#188); until then verify manually on a test account.

## 6. Incident response

Operators coordinate; community administrators lead every decision that touches community data. Incident records, tickets, and notifications carry identifiers and outcome only — never story/place/speaker content, media, URLs, credentials, or token values (SPEC-V2 §7 content-free rule).

### 6.1 Credential exposure (leaked secret, token, password, or recovery sheet)

1. **Contain.** Revoke the affected sessions immediately (account logout/revoke-all, admin revocation of member device sessions — R1). Regenerate recovery-code sheets (supersedes earlier codes — R6). Rotate the exposed secret per its runbook (R2-R5). For suspected account compromise, have a community admin reset the password or issue an admin login code (never for their own account); the reset revokes the account's sessions atomically (SPEC-V2 §7).
2. **Audit.** Review the affected communities' audit entries through the administrative API — logins, failed verifications, code issue/consume, session revocations, membership/role changes, file-authorization decisions. Check `AuthThrottle` backoff patterns for credential-stuffing. Entries carry actor/action/resource/outcome (+ IP/user-agent on auth events), which is exactly the evidence needed without exposing content.
3. **Recover.** Run each runbook's verification step and confirm old credentials fail. Confirm the affected accounts can re-authenticate through the assisted-recovery path.
4. **Notify/escalate.** The community's administrators decide whether and how to notify their members; operators support but do not substitute for that authority. Never disclose the credential value, the recovery sheet, or any cultural content. If the community has a steward, the steward's narrow authority (withdrawal/erasure/archive custody, SPEC-V2 §7) applies only through its recorded designation.

### 6.2 Suspected cultural-data access (cross-community read, super-admin overreach, export artifact or backup leak)

1. **Contain.** Disable implicated accounts — the authority-change triggers purge their sessions (SPEC-V2 §6.8). Suspend/cancel outstanding export download tokens; generated artifacts are already bounded by their token window (§7). For a leaked backup or export copy, isolate the storage location; deletion follows the §7 bounds and the runbooks above.
2. **Audit.** Review the audit entries for the affected community and actor: export requests/generation/downloads, file-authorization decisions, membership/role changes. Verify no log or observability sink holds content (they are content-free by contract — a violation is itself a reportable defect, §7).
3. **Recover.** The community's administrators choose the response. Withdrawal and erasure remain reachable through the sovereignty endpoints even while the community is disabled (SPEC-V2 §7); a restore may never target a point before a recorded erasure's completion, and post-completion restores reconcile before serving again.
4. **Notify/escalate.** Community administrators lead notification to their members; no public disclosure of cultural content — including in incident reports, issue trackers, or operator channels. Where administrators are unreachable, the recorded steward process carries the community's decision (SPEC-V2 §7); system privilege alone is never authority over community content.
5. **Close.** Record the incident with identifiers/outcome only; retention of the incident record itself follows the operator's own policy — it is not community content and must never become a secondary leak of it.

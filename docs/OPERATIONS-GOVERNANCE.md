# Operations governance: secrets, privacy, retention, incident response

**Status:** operator documentation for issue #150, subordinate to `docs/SPEC-V2.md`. Every retention number below is quoted from the spec (mainly Sections 5-7, 10) — this document may not drift from those values. Secret values live only in environment variables or platform secret stores, never in files, the repository, logs, or reports.

## 1. Startup configuration gate (#150)

Production deployments must fail closed on insecure or default critical configuration. `src/config/v2-runtime.ts` implements one shared validator used by both V2 entrypoints:

- **Node** (`src/hono-server.ts`): runs at startup before any adapter or database is opened; a refusal exits the process non-zero.
- **Workers** (`src/worker.ts`): runs at first request per binding set; a refusal returns `503 {"error":"Service unavailable","code":"config-refused"}` with `Cache-Control: no-store` and logs one line naming the offending settings, once per isolate. The body's `code` is stable and content-free, so a refused deployment is identifiable from the response alone — no retained log store is required — and the staging rollout health check (`docs/CLOUDFLARE-STAGING.md`, `/health`) catches the refusal at deploy time, before community traffic.

Mode selection: `NODE_ENV` (Node) and `ENVIRONMENT` (Workers binding) accept `development`, `test`, `production`, `field-kit`, `offline`; **unset means production**; unknown values are refused. `production`, `field-kit`, and `offline` enforce the production rules; only `development` and `test` relax them. A deployment that starts in a relaxed mode is never silent: the entrypoint logs a one-line content-free marker naming the mode at startup (Node) or once per binding set (Workers), and the gate refuses `development`/`test` outright when the configured public origin is `https` on a non-loopback host — a deployed origin is a production signal a relaxed mode may not serve. Local development keeps working: it uses loopback or plain-HTTP origins, or no origin at all.

**Container profiles.** The `production` image and the production/field-kit Compose files start the Node V2 entrypoint (`dist/hono-server.js`) after `dist/db/migrate.js`; they pass `HONO_PUBLIC_ORIGIN`, `AUTH_SERVER_SECRET` and `BOOTSTRAP_SECRET` (required, no defaults) so a misconfigured container refuses to start. `HONO_HOST` (default `127.0.0.1`) is set to `0.0.0.0` inside the image so the published port or nginx can reach it. Docker CI checks `/health` and `/v2/bootstrap` on the built image. Node profiles (self-hosted SQLite/PostgreSQL and field kit) therefore run `dist/hono-server.js`; Fastify (`dist/server.js`) is development-only. `/health` is liveness (process up, used by the container healthcheck); `GET /ready` reports readiness for orchestrators and load balancers that should stop routing during a database outage.

| Setting (Node / Workers)                                 | Refused when                                                                                                                                                                                     |
| -------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `NODE_ENV` / `ENVIRONMENT`                               | value is not one of the five known modes (unset is allowed and means production); a relaxed mode (`development`/`test`) combined with an `https` public origin on a non-loopback host            |
| `HONO_PUBLIC_ORIGIN` / `PUBLIC_ORIGIN`                   | missing in a production-like mode; not an exact origin; not `http(s)`; a template placeholder; a loopback host; an unspecified bind-any host (`0.0.0.0`, `[::]`); `http` where https is required |
| `HONO_CORS_ORIGINS` / `CORS_ORIGINS`                     | any entry is a wildcard (`*`), not an exact origin, a placeholder, or `http` where https is required (credentialed CORS needs an exact allowlist)                                                |
| session cookie `Secure` flag                             | disabled where https is required (only `development` disables it on the Node entrypoint — `test` keeps `Secure`; the field-kit plain-HTTP opt-in may)                                            |
| `HONO_PORT` (Node only)                                  | not an integer in 1-65535                                                                                                                                                                        |
| `AUTH_SERVER_SECRET`                                     | missing in a production-like mode; shorter than 32 characters; a template placeholder                                                                                                            |
| `BOOTSTRAP_SECRET` (Node) / `BOOTSTRAP_SECRET` (Workers) | missing in a production-like mode; shorter than 24 characters; a template placeholder                                                                                                            |

Messages name the setting, never its value. Placeholder detection covers, case-insensitively: `change-me`/`change_me`/`changeme`, `replace-with`/`replace_with`/`replacewith`, `00000000-`, `placeholder`, hostnames starting `your-`/`replace`/`change-me`, the documentation hosts `example.org`/`.com`/`.net` and their subdomains, the reserved TLDs `.example`, `.invalid`, `.test`, `.localhost`, and (in production-like modes) loopback hosts — including IPv4-mapped IPv6 loopback in the URL parser's canonical hex spelling `[::ffff:7f00:1]` — and unspecified bind-any hosts. The committed `wrangler.jsonc` is a template whose `replace-with-*` names and `https://example.org` origin are exactly what the gate refuses in production.

**Plain-HTTP exception (SPEC-V2 §7).** Field kits serve HTTPS by default via a device-local CA. Plain HTTP on a trusted LAN is allowed only on Node `field-kit`/`offline` modes with the explicit opt-in `HONO_ALLOW_PLAIN_HTTP=true`; it is never available on Workers or in `production` mode, and while enabled the admin UI shows a persistent warning and the readiness report flags the build (SPEC-V2 §7). Non-Secure cookies follow the same boundary.

**Layering with the V1 gate.** On Node, `src/shared/config/schema.ts` still rejects missing, shipped-placeholder, or sub-32-character `JWT_SECRET`/`SESSION_SECRET` in production/field-kit modes when the shared database bootstrap loads configuration; the V2 gate fires first at startup. The V2 runtime gate (#150) requires the first V2 configuration secret — the prelogin `AUTH_SERVER_SECRET` (SPEC-V2 §7) — and the installation bootstrap secret — `BOOTSTRAP_SECRET` (SPEC-V2 §7, PR #252) — in every `production`/`field-kit`/`offline` mode: missing, sub-32-character (or sub-24 for `BOOTSTRAP_SECRET`), or placeholder values refuse startup (Node) or serving (Workers), and messages name only the setting. `development` and `test` do not require them. The inventory rows are below.

**Tests:** `tests/config/v2-runtime.test.ts` (every rule, plus dev/test acceptance), `tests/hono/worker-config.test.ts` (workerd serve refusals and valid-production serving), `tests/config/v2-runtime-startup.test.ts` (Node process exits non-zero, before the database opens).

## 3. Rotation and revocation runbooks

Each runbook ends with a verification step. "Automated" cites the test that proves the property; where no automated test exists yet, the manual check is stated and the owning work is named.

**R1 — V2 sessions (revocation).** The account logs out, or calls revoke-all; a community admin revokes a member's device sessions by metadata; user/community authority changes delete sessions via database triggers (SPEC-V2 §6.8).
_Verify (automated):_ `tests/hono/foundation.test.ts` and `tests/hono/worker.test.ts` prove the presented cookie stops authenticating immediately after logout/revoke, that login rotation binds a fresh row while the old token fails, and that requests fail closed when authoritative session state is unreadable. _Operator spot check:_ replay the old cookie — expect `401`.

**R2 — `JWT_SECRET` / `SESSION_SECRET` (V1 runtime).** Generate a new value (`openssl rand -base64 48`), replace it in the deployment environment (never in a file or the repository), and restart the deployment. Compose files require both variables (`:?` guard).
_Verify (automated):_ the production config gate rejects placeholders and values shorter than 32 characters — `tests/config.test.ts` ("rejects shipped production placeholder", "must be at least 32 characters in production"). _After rotation:_ previously issued tokens and sessions stop validating — replay an old session cookie/authorization, expect `401`.

**R3 — PostgreSQL credential.** Rotate from an interactive `psql` admin session with `\password terrastories`: the prompt reads the new value without echoing it and sends a parameterised statement, so only the verifier hash reaches the server — the plaintext never lands in shell history, `ps`/`/proc`, or a client statement log (never `ALTER ROLE ... PASSWORD '...'` on the command line). Update `DATABASE_URL` in the deployment environment — environment variable, platform secret store, or an env file with mode `0600` and no other reader — never a tracked file or a command-line argument. Restart. V2 sessions are database-backed and survive the rotation.
_Verify:_ connect with the old URL — authentication must fail; with the new deployment up, `GET /ready` returns `{"status":"ready"}`.

**R4 — Field-kit local CA key.** Generate a replacement CA, reissue the certificate covering every configured host name and IP, re-enroll devices against the new CA fingerprint (shown in the admin UI and on the printed recovery sheet), then destroy the old key file. A leaked key requires exactly this: replace the CA and re-key all enrolled devices (SPEC-V2 §7).
_Verify:_ a device still pinned to the old fingerprint must fail TLS trust; the readiness report shows the new fingerprint and continues to flag the build if the plain-HTTP exception is enabled.

**R5 — Cloudflare API token.** Roll the token in the Cloudflare dashboard (keep it scoped), update the operator environment.
_Verify:_ `npx wrangler whoami` fails with the old token and succeeds with the new one (command outline in `docs/CLOUDFLARE-STAGING.md`).

**R6 — Recovery codes.** The account holder regenerates the set through the authenticated step-up action, which re-verifies the current password; regeneration marks every earlier code superseded (SPEC-V2 §6.8).
_Verify:_ an earlier code must fail redemption with the uniform non-enumerating login failure. An automated regeneration-supersession test lands with the authentication work (#137/#188); until then verify manually on a test account.

## 6. Incident response

Operators coordinate; community administrators lead every decision that touches community data. Incident records, tickets, and notifications carry identifiers and outcome only — never story/place/speaker content, media, URLs, credentials, or token values (SPEC-V2 §7 content-free rule).

### 6.1 Credential exposure (leaked secret, token, password, or recovery sheet)

1. **Contain.** Revoke the affected sessions immediately (account logout/revoke-all, admin revocation of member device sessions — R1). Regenerate recovery-code sheets (supersedes earlier codes — R6). Rotate the exposed secret per its runbook (R2-R5). For suspected account compromise, have a community admin reset the password or issue an admin login code (never for their own account); the reset revokes the account's sessions atomically (SPEC-V2 §7).
2. **Audit.** Review the affected communities' audit entries through the administrative API — logins, failed verifications, code issue/consume, session revocations, membership/role changes, file-authorization decisions. Check `AuthThrottle` backoff patterns for credential-stuffing. Entries carry actor/action/resource/outcome (+ IP/user-agent on auth events), which is exactly the evidence needed without exposing content.
3. **Recover.** Run each runbook's verification step and confirm old credentials fail. Confirm the affected accounts can re-authenticate through the assisted-recovery path.
4. **Notify/escalate.** The community's administrators decide whether and how to notify their members; operators support but do not substitute for that authority. Never disclose the credential value, the recovery sheet, or any cultural content. If the community has a steward, the steward's narrow authority (withdrawal/erasure/archive custody, SPEC-V2 §7) applies only through its recorded designation.

### 6.2 Suspected cultural-data access (cross-community read, super-admin overreach, export artifact or backup leak)

1. **Contain.** Disable implicated accounts — the authority-change triggers purge their sessions (SPEC-V2 §6.8). Before disabling an account that is a community's only reachable administrator, record the containment decision and notify the community's recorded steward, if any: disabling the last administrator destroys the authority the recovery step below depends on, and the order is deliberate — record or transfer authority first, then contain. A withdrawal or erasure request already recorded before the disablement survives it and is executed by operators on the community's behalf; operators execute recorded requests but never initiate them. Sole-administrator lockout with no steward and no recovery path is the SPEC-V2 §7 open question — escalate it rather than improvise authority. Suspend/cancel outstanding export download tokens; generated artifacts are already bounded by their token window (§7). For a leaked backup or export copy, isolate the storage location; deletion follows the §7 bounds and the §5 retention table.
2. **Audit.** Review the audit entries for the affected community and actor: export requests/generation/downloads, file-authorization decisions, membership/role changes. Verify no log or observability sink holds content (they are content-free by contract — a violation is itself a reportable defect, §7).
3. **Recover.** The community's administrators choose the response. Withdrawal and erasure remain reachable through the sovereignty endpoints even while the community is disabled (SPEC-V2 §7); a restore may never target a point before a recorded erasure's completion, and post-completion restores reconcile before serving again. Hold the orphan sweep during any restore — see §6.4.
4. **Notify/escalate.** Community administrators lead notification to their members; no public disclosure of cultural content — including in incident reports, issue trackers, or operator channels. Where administrators are unreachable, the recorded steward process carries the community's decision (SPEC-V2 §7); system privilege alone is never authority over community content.
5. **Close.** Record the incident with identifiers/outcome only; retention of the incident record itself follows the operator's own policy — it is not community content and must never become a secondary leak of it.

### 6.4 Restore hold for the orphan sweeper

The restart-safe orphan sweeper (SPEC-V2 §6.7) deletes stored objects that no `files` row references and that are older than the 24-hour grace window. A filesystem/database restore can recreate storage bytes _before_ the `files` table knows them; the bytes then look like garbage and would be swept. The sweeper therefore has an explicit restore hold, checked at the start of every run. The sweep deletes nothing while either hold is in effect:

1. **Environment/config flag** — `ORPHAN_SWEEP_PAUSED=true` (see `.env.example`). On the Node entrypoint it is read from the process environment; on Workers it is the `ORPHAN_SWEEP_PAUSED` binding. Parsing is case-insensitive and fail-closed: only an empty value or `false`/`0` (any case, surrounding whitespace ignored) leaves the sweep running — `TRUE`, `1`, `yes`, `on` or any other value pauses it.
2. **Storage marker object** — `system/orphan-sweep-hold`, read through the storage adapter. It lives outside the swept `communities/` and `users/` prefixes, so the sweep never deletes it and the hold cannot dissolve itself; it is removable only by the operator who set it. An unreadable marker is treated as set (keeping bytes is always safe). An adapter without system-object access cannot carry a marker and sweeps normally.

Operator procedure for any restore (D1 Time Travel, retained D1 export, self-hosted/field-kit file backup):

1. Set the hold _before_ touching the restore — `ORPHAN_SWEEP_PAUSED=true`, or create the marker (self-hosted Node: `touch <storage-root>/system/orphan-sweep-hold`; Workers: put an empty `system/orphan-sweep-hold` object in the MEDIA bucket through the pinned CLI: `npx wrangler r2 object put <bucket>/system/orphan-sweep-hold --file /dev/null --remote`). On the hosted profile the sweep runs **hourly** (`0 * * * *`), so the hold is the only thing closing the window between a D1 Time Travel restore landing and storage and the database agreeing — an unheld restore can lose restored bytes to the next hourly run.
2. Restore, then verify the restored state against the out-of-band erasure records and the files table before serving (SPEC-V2 §7, "Backups" — restores may never target a point before a recorded erasure's completion; post-completion restores reconcile before serving again — applied in practice at this document's §5 and the Recover step of §6.1/§6.2).
3. Lift the hold only after verification — unset the flag or remove `system/orphan-sweep-hold`. The Node sweep additionally never runs at boot; its first run is delayed (named constant, default 1 hour) so a restore in flight at process start is not raced.

Neither hold touches the database; lifting the hold never deletes anything by itself — it only re-enables the normal sweep, which still honors the grace window, the reference check and the resume cursor.

### 6.5 Restore drills, RPO/RTO targets and rollback policy

Restores are rehearsed in CI, offline, by `tests/drills/*.test.ts` (`npm run test:drills`). Each drill seeds a two-community dataset, takes the profile's backup, restores into a fresh database, then asserts identical row counts and per-table SHA-256 checksums, the community-ownership invariants (edges, attachments, storage keys and sessions never cross a community), an integrity/foreign-key check, and writes `restore-drill-<profile>.json` (CI artifact `restore-drill-reports`) recording the schema/migration journal head, per-table digests and measured elapsed time.

**Forward-fix versus rollback.**

1. Default to **forward-fix**. A defective migration or release is repaired by a new migration or code deploy (expand/contract, SPEC-V2 section 8); Worker/Node code rollback is separate from the data and never needs a restore.
2. **Roll back data** (restore) only for loss or corruption that a forward change cannot repair, chosen by the community administrators with the operator (section 6.2). The restore point may never precede a recorded erasure's completion (SPEC-V2 section 7, Backups).
3. Every restore follows 6.4 (hold the orphan sweep first), then: restore into a fresh database, run the **post-restore step** on the restored database before serving: `npx tsx scripts/ops/post-restore.ts <sqlite-file | postgresql-url>` deletes every `sessions` row, supersedes every unconsumed `login_codes` row (recovery and admin_issued) and `claim_tokens` row, and deletes `export_tokens` (a backup carries credentials the community may have revoked or consumed since; revocation is delete-based and consumption is a row update, so a restored file would revive them — every drill runs the step and asserts it), reconcile against the out-of-band erasure records, verify, then lift the hold and re-rotate or destroy the restored copy under the profile bound.
4. Record the schema/migration version of the backup against the running release before restoring; a backup older than the deployed migration is restored, then migrated forward, never the reverse.

**Account changes revert to backup time.** The post-restore step cannot undo password hashes/verifiers, roles, community membership and `is_active` rolling back: a user disabled, demoted or re-credentialed after the backup is active, privileged or on the old password again after restore. Keep the pre-restore database file as the frozen source (do not delete it until reconciliation ends) and replay from its `audit_entries` the actions after the backup's highest audit id: `user.create`, `user.update`, `user.password_reset`, `user.session.revoke`, `user.login_code_issue`, `auth.password.change`, `auth.identifier.change`, `auth.recovery.redeem`, `auth.recovery_codes.generate`, `claim_token.issue`, `claim_token.consume`. `replayAccountChanges` in `scripts/ops/post-restore.ts` copies the authority columns of every user those entries touched from the frozen database onto the restored one (the SQLite drill disables a viewer after the backup and proves login is refused after the replay); review the replayed ids, then run the post-restore step's session purge again. The PostgreSQL profile replays the same list by hand from the frozen database.

**Field-kit uploads.** `field-kit-backup.sh` copies every upload regardless of age and writes a manifest of all files; the drill ages a file past 7 days and asserts it restores byte-identical and that every manifest entry exists in the archive. Backup size grows with the media volume, so size the backup volume for a full copy per retained backup (`BACKUP_RETENTION_DAYS`). The script is POSIX sh (the backup service runs the app image, Alpine/BusyBox), takes a consistent online copy of every SQLite database (`scripts/ops/sqlite-backup.mjs`, never a raw file copy), fails the whole backup on any failed copy, and writes the archive mode 0600. Treat archives as content-bearing: they hold community content and password verifiers.
